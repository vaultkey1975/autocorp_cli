# AI Engineering Constitution — AutoCorp CLI

This is the permanent, non-negotiable rule set for any AI engineer working
in this repository. It does not expire with a session and is not
superseded by a task prompt unless that prompt is from the repository
owner and explicitly says so. If a task instruction conflicts with this
document, follow the task instruction for that task, but do not treat the
conflict as license to violate this document in future work.

---

## 1. Mission

AutoCorp CLI is a local, terminal-first AI coding assistant. Its job is to
plan, build, test, explain, and — as of the current body of work — safely
analyze, repair-propose, and validate both itself and external target
repositories (currently CloneCast, at `/home/larry/clonecast`), entirely
offline where possible (Ollama) and without ever silently mutating
production state. Every AI engineer's mission inside this repository is to
extend that capability without weakening any of the guarantees below.

---

## 2. Repository Safety

- Never delete, rename, or move a file unless the task explicitly requires
  it and you have confirmed (via `git status`) what you are about to
  discard is either committed elsewhere or genuinely disposable.
- Never modify a target system outside this repository (currently
  CloneCast) except through its own public services/routes/CLI, and never
  without first proving — via independent SHA-256/`git status` checks you
  perform yourself, not ones a prior report claims — that the target's
  production database and working tree are unchanged after your work.
- Never run a destructive git operation (`reset --hard`, `push --force`,
  `clean -f`, branch deletion) without explicit owner instruction.
- Never commit or push unless explicitly asked. Creating a commit is not
  the same as finishing a task — see `PHASE_COMPLETION_POLICY.md`.
- Treat `/tmp` disposable-workspace directories, the SQLite databases under
  `data/`, and anything under `workspace/` as regenerable scratch — but
  still verify before deleting anything you did not create yourself in the
  current session, since another process's in-progress work can look like
  disposable scratch from the outside (this repository has, in its own
  history, had prior sessions leave uncommitted work in the tree that a
  later session correctly chose not to discard).

## 3. Source of Truth

The repository — its committed history, its current working tree, its
passing/failing tests, and the output of commands you run yourself — is
the only source of truth. A prior AI-generated report, a commit message, a
branch name, or a document in this folder is evidence to be checked
against the repository, never a substitute for checking the repository.

This repository already contains concrete proof of why this matters:
`README.md` still describes the very first commit's architecture, dozens
of commits after it stopped being accurate. Do not let any document in
`AI_ENGINEERING/` suffer the same fate — and do not trust one that already
might have, without re-verifying against the repository first.

## 4. Evidence Requirements

A claim of "this works" or "this is complete" requires at least one of:

- A test that exercises the actual behavior and passes when you run it
  yourself, right now, in this session.
- A verification report generated by actually running the system against
  real dependencies (not a report that only describes what the system is
  supposed to do).
- Direct inspection of the code path in question, cited by file and line.

A claim is NOT evidence merely because:

- A commit message says "complete," "done," or "fixed."
- A branch exists with a promising name.
- A prior report says something passed, if you cannot find the artifact or
  reproduce the result yourself.
- The feature "should work" based on the design.

If evidence conflicts — a commit message claims completion but there is no
passing test, or two reports disagree — report the conflict explicitly.
Do not silently resolve it by picking whichever answer is more convenient.

## 5. Definition of Done

Work is done only when:

1. The code change exists and is committed (or the task explicitly forbids
   committing, in which case "done" means ready-for-owner-review, not
   "complete").
2. The full test suite passes (`.venv/bin/python -m pytest -q`), and you
   report the exact pass/fail/xfail counts and exit code, not a summary.
3. Any new capability has a test that would fail if the capability were
   removed or broken.
4. Any relevant document under `AI_ENGINEERING/` has been updated to match
   reality (see `DOCUMENTATION_POLICY.md`).
5. `git status` has been checked and its state is accurately reported —
   "done" and "uncommitted" are not mutually exclusive descriptions of the
   same work; both must be stated.

## 6. Testing Standards

- Every new module gets real unit tests for its pure/deterministic logic.
  This repository's own practice (see `tests/`, 93+ tracked test files) is
  to test helper functions directly rather than only through end-to-end
  paths — follow it.
- Do not write a test that mocks the very thing it claims to verify. This
  repository's own `brains/workflow_test.py` and `brains/quick_podcast_runner.py`
  exist specifically to prove real behavior against a real (disposable)
  target rather than trusting mocked responses, for exactly this reason.
- Where a real external dependency cannot be exercised safely (a live
  Chatterbox GPU render, a real Ollama call, a real CloneCast instance),
  either exercise it for real inside a disposable/isolated environment (the
  established pattern in this repository) or state plainly that the path
  is untested and why.
- Run the full suite, not just the new tests, before reporting completion.
  This repository has caught real regressions (unclosed file handles
  surfacing only under `-W error` across the full suite) that a
  single-file test run would not have caught.

## 7. Documentation Standards

- Documentation describes what the repository evidence supports — not what
  a phase was originally planned to do, not what would be nice, not what a
  future phase might need.
- Every one of this repository's own `[Phase N]`-labeled modules already
  documents its own scope in its module docstring. When in doubt about what
  a module actually does, read the module before writing about it.
- Do not restate marketing language ("production-grade," "enterprise-ready")
  that is not backed by a specific, checkable fact.

## 8. Git Standards

- Prefer small, single-purpose commits with descriptive messages, matching
  this repository's established style (`git log --oneline` shows short,
  imperative, specific subjects — follow that pattern, not a generic one).
- Never amend a commit unless explicitly asked; create a new one.
- Never use `--no-verify` or otherwise bypass hooks unless explicitly
  instructed.
- Do not tag a release. This repository's tags (`v0.1.0`–`v0.10.5`) are
  owner-controlled; they stop 49 commits before current `HEAD` and have not
  been extended by any AI session since — that is the owner's call to make,
  not an AI engineer's.

## 9. Regression Prevention

- Before changing shared code (anything imported by more than one module —
  `brains/scanner.py`'s public helpers are a documented example, reused by
  `brains/analyzer.py`, `brains/project_planner.py`, `brains/repair_proposal.py`,
  and `brains/workflow_test.py`), grep for every caller and confirm your
  change doesn't silently alter their behavior.
- Run the full test suite after any change, not only the tests for the
  file you touched.
- If you rename a private helper to make it public for reuse (an
  established, precedented pattern in this repository), verify no other
  code already referenced the private name before the rename.

## 10. Architecture Rules

- The brains never touch the filesystem or shell directly outside their own
  designated seam (`Executor` + `CommandGate` for the original build loop;
  disposable-workspace + explicit `--disposable`/`--test` flags for the
  newer validation tooling). Do not add a new code path that bypasses this.
- Anything that targets an external system (CloneCast) must operate through
  a disposable copy of that system's data, never its production database or
  working tree, and must independently verify (SHA-256 + `git status`, not
  a trust-the-caller assumption) that production was unaffected.
- Anything that could reach a real external network destination (an
  upload, a publish, a paid API) must default to refusing unless an
  explicit safety flag is present, and must be provably incapable of
  reaching that destination during automated verification (this
  repository's Phase 1Y work is the concrete precedent: it proved the
  upload boundary by checking a machine-readable `upload_status` field
  rather than merely trusting that no network call had been coded).

## 11. Coding Standards

- No placeholders, no stub functions, no `pass`-only implementations
  presented as working code, no fabricated success paths. Where the
  existing codebase uses a bare `pass` intentionally (an abstract-method
  interface, a deliberately-swallowed narrow exception), it is commented
  with why — match that convention, don't leave an uncommented one.
- No hardcoded values standing in for what should be computed from real
  repository/system state (this repository's `brains/scanner.py` and
  `brains/analyzer.py` docstrings both state this as a hard requirement,
  and it has been enforced in every phase since).
- Prefer editing existing files and reusing existing helpers over
  duplicating logic — this repository has an explicit, working precedent
  (`brains/scanner.py` exposing `iter_python_files`/`is_test_file`/
  `count_markers` specifically so `brains/analyzer.py` didn't have to
  reimplement them).

## 12. Production Rules

- No fake repository scans, no fake verification, no fake success. If a
  verification step cannot run (a missing dependency, an unreachable
  service, a blocked external system), report that plainly — do not report
  a synthetic pass.
- Any tool that inspects or reports on this repository or a target system
  must derive every number it reports from that system at run time. This
  is a hard, repeated, explicit requirement across every scanning/analysis
  module in this repository's history (`scanner.py`, `analyzer.py`,
  `project_planner.py`, `live_readiness.py`) and applies equally to new work.

## 13. Future AI Compatibility

- Nothing in this repository or its documentation should assume a specific
  AI model, vendor, or tool. Where a model is named in code (e.g. the
  default Ollama model in `config.py`), it is a configurable default, not
  an architectural assumption.
- Any AI engineer — regardless of which model is running it — is bound by
  this document equally. `BOOTSTRAP_PROMPT.md` is model-agnostic on purpose.

## 14. Documentation Maintenance

- These documents are living, but only if they are actually kept current.
  Whoever changes the state they describe is responsible for updating them
  in the same unit of work — not "later," not "in the next session."
- If you find a document in `AI_ENGINEERING/` that has gone stale relative
  to the repository, fix it as part of your current task rather than
  leaving it for the next engineer, and note the correction in
  `CHANGELOG_AI.md`.
