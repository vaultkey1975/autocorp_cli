7. Repository discovery
-------------------------
`autocorp_testing/discovery.py` inspects, read-only: pyproject.toml,
pytest.ini, setup.cfg, tox.ini, noxfile.py, Makefile, conftest.py, README*,
.github/workflows/*.yml, .gitlab-ci.yml, azure-pipelines.yml, test roots
(directories containing test_*.py/*_test.py), dependency/lock files
(requirements*.txt, pyproject.toml, poetry.lock, Pipfile[.lock], setup.py/cfg,
uv.lock), migration directories (migrations/, alembic/), pytest markers
(from ini-style `markers =` blocks), the target's own venv
(.venv or venv, else falls back to the current interpreter), and
pytest's installed version.

Strict full command discovery priority: (1) `.autocorp/test-profile.json`
"strict_full_command" override, (2) CI workflow step lines that look like a
real pytest invocation, (3) Makefile test targets / tox.ini `commands` /
noxfile.py `session.run("pytest", ...)`, (4) README fenced/backtick lines
that look like a real invocation, (5) presence of a pytest config file alone
(pytest.ini/pyproject/setup.cfg) as medium/high-confidence evidence that
`<venv_python> -m pytest` is the strict command (pytest then applies the
repo's own addopts/testpaths). A shared `_looks_like_pytest_invocation()`
filter rejects false positives such as "pip install pytest" or README prose
that merely mentions the word "pytest" (this was caught and fixed during
this phase - see Known Limitations).

For AutoCorp's own repository the discovered strict command is:
  /home/larry/autocorp_cli/.venv/bin/python -m pytest
(confidence: medium - no CI/README/-W error evidence exists in this repo;
pytest.ini's own `addopts = -q` and `testpaths = tests` govern the rest).

Compile command discovery: uses the target's own scripts/verify_compileall.py
if present (AutoCorp's own repo has one), else falls back to
`<venv_python> -m compileall -q <repo>`.


8. Change detection
---------------------
Uses only read-only Git subcommands (status --porcelain, diff --name-only,
rev-parse). Detects staged, unstaged, and untracked files; committed diffs
against an explicit --base-branch; and accepts explicit --path/--node-id
selectors. Verified never to modify the target repository (see
test_change_detection_never_writes_to_the_repository and
test_no_target_repository_modification_in_fast_mode).

Repository fingerprint = SHA-256 over: repo path, branch, commit SHA, sorted
changed file paths, per-file content hashes, config-file content hashes
(pytest config + conftest.py + dependency files + migration dirs), Python
version, and pytest version.


9. Test mapping
------------------
Combines, per changed file: (1) filename matching (module basename appears
in a test file's basename), (2) import analysis (AST-parsed test file
imports checked against the changed module's dotted name), (3) one-hop
dependency expansion (tests of any module that imports the changed module
are pulled in, reason: "dependency expansion: ..."), (4) feature/symbol
matching for --feature (test file name / function name / class name /
body text, plus source symbols that import into a matching test), and
(5) explicit `.autocorp/test-profile.json` "explicit_mappings" and
"feature_to_test_mappings". Mandatory safety tests are pulled from the
profile's "always_run_safety_tests" plus a built-in heuristic (file name
contains "safety" or "_gate" - this matched AutoCorp's own
tests/test_gate.py, tests/test_acceptance_gate.py, etc.).

When a changed file has zero direct/import matches, the engine does not
silently guess broadly - it records an explicit uncertainty warning instead
(see test_conservative_handling_of_uncertainty), which surfaces in both the
human report and `uncertainty_warnings` in the plan/JSON.

Every selected test carries its full reasons list; this is enforced by
test_selection_reasons_are_recorded_for_every_selected_test and is visible
directly in the JSON `selection_reasons` field.


10. Test ordering
--------------------
FAST/FOCUSED order by category: previously_failed -> syntax -> import ->
direct/feature/explicit -> safety -> integration -> slow (name hints:
"slow", "workflow", "live_test", "publish") -> dependency. FULL is never
reordered - it runs the repository's own discovered command exactly as
given.


11. Timing and result history
--------------------------------
Stored in AutoCorp's own managed data area at
data/fast_pytest_engine/history.db (SQLite; never inside the target
repository - verified for an external disposable repo in the test suite).
Records repo path, node id/path, branch, commit SHA, repository and config
fingerprints, duration, result, failure type, last run time, python/pytest
versions, the exact command run, mode, and GPU/DB/network classification.
No secrets are stored (no environment variables, no credentials).

Cached passes are never treated as proof of a run: FAST/FOCUSED/FULL always
execute pytest for real (verified by
test_stale_pass_results_never_replace_execution, which seeds a fake
"passed" history entry, then breaks the real source, then asserts test-fast
actually fails).


12. Cache invalidation
-------------------------
A test's timing estimate is labeled stale (not deleted) whenever the
config fingerprint - built from the pytest config file(s), conftest.py,
dependency/lock files, migration directories, Python version, and pytest
version - differs from what was stored. Verified directly for: conftest.py
changes, pytest.ini changes, requirements.txt changes, and migration file
changes (each produces a different fingerprint), and for the timing-estimate
staleness label itself.


13. Parallelism strategy
----------------------------
pytest-xdist is not installed in this environment's venv, so parallelism is
currently reported as disabled with an explicit reason
("pytest-xdist is not installed in the target environment") for every run
against this repository - this was confirmed directly
(`.venv/bin/python -c "import xdist"` fails). When xdist is available, the
engine additionally refuses to parallelize if any selected test's source
mentions shared-state signals (sqlite3.connect, .db paths, fixed ports,
os.environ mutation, globals, /tmp paths); otherwise it picks a conservative
worker count (min(4, cpu_count // 2)). Both the safe and unsafe paths are
covered by tests (test_safe_xdist_decision_when_installed_and_no_shared_state,
test_unsafe_shared_database_decision_disables_parallelism).


14. GPU safety
-----------------
Keyword-based classification (cuda, torch.cuda, chatterbox, gpu, nvidia,
ollama, video_lab, diffusers) flags a selected test as GPU-involving; such
tests are listed under `gpu_safety.gpu_tests_detected` and surfaced as a
deferred check ("real GPU runtime verification ... deferred"). No GPU
inference, no Chatterbox run, and no video-model run occurred anywhere in
this phase. No GPU process was killed (none was ever started).


15. Database safety
-----------------------
Keyword-based classification (sqlite3, .db paths, postgres, sqlalchemy,
migrations, etc.) flags database-involving tests and reports
`disposable_data_required: true` for them. A separate production-DB guard
(`safety.snapshot_production_db` / `verify_production_db`) hashes a
configured production DB path before and after a run and reports
`changed_unexpectedly` if the SHA-256 differs - covered directly by
test_production_db_guard_detects_unexpected_change and
test_production_db_guard_reports_unchanged. No production database was
touched during this phase; AutoCorp's own data/autocorp.db was never opened
by the engine (only the target repository's Python source and test files are
read).


16. JSON contract
--------------------
`EngineReport.to_dict()` / `TestPlan.to_dict()` emit exactly the field names
specified in the mission (schema_version, mode, repository,
repository_fingerprint, changed_files, selected_tests, selection_reasons,
commands, results, duration_seconds, deferred_checks, full_suite_required,
production_approval_allowed, parallelism, gpu_safety, database_safety,
errors), plus additive fields (passed, failed, exit_code, blocked,
blocked_reason, compile_result, import_check_results) that do not rename or
remove any required field. Verified JSON-serializable and schema-stable by
test_json_schema_has_stable_required_fields and
test_cli_test_fast_json_output_is_valid_json.

tests/test_guided_clonecast_episode_operator.py directly (not just via

  - AutoCorp calls supported CloneCast CLI commands only, via

  - Real CloneCast IDs are required: episode_id, script_id,

  - Mastered audio (final_audio) is used for owner review in

    preserved separately in artifact_paths and also printed.
  - Sessions resume correctly via `--resume SESSION_ID`
    (load_session + repo-path identity check).
  - Completed voice sections are preserved: regenerate_section refuses to
    rebuild a section already in validation_evidence["approved_sections"].
  - Mastering can retry without rerunning successful TTS:
    _master_existing_episode only re-invokes episode-audio-master using the
    already-stored episode_audio_job_id; it never re-calls speech-render.
  - Publishing is locked by default (owner_approval_status starts
    "publishing_locked") until owner_approval_status is switched to
    "publishing_eligible" by approve_for_publishing.
  - Approval only grants publishing eligibility - approve_for_publishing

    CloneCast publish/publication-* command

  - CloneCast failures are reported truthfully: CloneCastCLI.checked()

  - No placeholders, fake audio paths, hardcoded success, or silent

22. Known limitations
-------------------------
  - Test selection granularity is file-level for FAST/FOCUSED (a whole test
    file is chosen or not); only explicit --node-id targets a single test
    function. This is a deliberate simplicity trade-off - pytest's own
    -vv output still reports and records real per-test results.
  - Strict-command discovery is heuristic (CI/Makefile/tox/noxfile/README
    text matching). It was caught mis-detecting "pip install pytest" and a
    README example string containing the word "pytest" as commands during
    this phase's own testing and was fixed (see Section 7); other unusual
    formats could still evade detection, in which case test-full correctly
    reports BLOCKED rather than guessing.
  - Parallelism has only been exercised in its "disabled" branch on this
    machine, since pytest-xdist is not installed here; the "enabled" branch
    is covered by a focused unit test but not by a real multi-worker run
    against this repository.
  - Dependency-expansion mapping is one hop only (tests of direct importers
    of a changed module), not a full transitive closure, to keep FAST
    genuinely fast and avoid runaway selection growth on large repositories.
  - The mandatory-safety-test heuristic (filename contains "safety" or
    "_gate") is a simple default; repositories with differently-named
    safety-critical tests should list them explicitly in
    `.autocorp/test-profile.json`.
